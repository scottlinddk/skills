Umbraco changed shape at version 14, so the **major version** decides almost every answer. Read it first, from the `Umbraco.Cms` package reference in the `.csproj` or `Directory.Packages.props`, and say which major you are working against before proposing anything.

## The split

| | Umbraco 13 and earlier | Umbraco 14 and later |
| --- | --- | --- |
| Backoffice | AngularJS | Web components (Lit), TypeScript |
| Extension manifest | `App_Plugins/<Name>/package.manifest` | `App_Plugins/<Name>/umbraco-package.json` |
| Backoffice talks to the server through | AngularJS resources and backoffice controllers | the Management API |

Long-term support, as published on [Umbraco's LTS and EOL page](https://umbraco.com/products/knowledge-center/long-term-support-and-end-of-life/) (read it again for today's dates before advising on an upgrade):

- **13** (LTS, .NET 8): end of life 14 December 2026.
- **17** (LTS, .NET 10): released 27 November 2025, security phase from 27 November 2027, end of life 27 November 2028.
- The majors between and after them are short-lived releases.

## Docs are per major

The documentation is versioned in its URL: `https://docs.umbraco.com/umbraco-cms/<major>.latest/...` (for example `17.latest`, `13.latest`). Read the page for the repo's major before writing against any Umbraco API. Recalled Umbraco code mixes majors freely, and a v13 answer in a v17 repo compiles nowhere.

## Where things live

- **Schema** (document types, data types, templates) lives in the database. Look for a serialization tool before changing it: a `uSync/` folder, or Umbraco Deploy files under `umbraco/Deploy/`. Where one exists, schema changes travel as those files in the same commit as the code that needs them. Where none exists, tell the user the change is a manual backoffice step and list it.
- **Models** are generated by ModelsBuilder; the mode is in `appsettings.json` under `Umbraco:CMS:ModelsBuilder`. Generated model files are regenerated, never edited: extend them with a partial class.
- **Registration** goes through an `IComposer`, which is where services, notification handlers and options are added to DI.
- **Headless** content is the Content Delivery API, switched on under `Umbraco:CMS:DeliveryApi` in `appsettings.json`. A React client reads from it; it is the contract, so treat changes to exposed content types as API changes.

## Backoffice extensions on 14 and later

An extension is a web component registered by a manifest. The parts, from [Creating your first extension](https://docs.umbraco.com/umbraco-cms/extend-your-project/tutorials/creating-your-first-extension):

- `umbraco-package.json` declares each extension (type, alias, the element's JavaScript file). Add its `$schema` for editor validation.
- The element extends `UmbElementMixin(LitElement)`, importing Lit from `@umbraco-cms/backoffice/external/lit` so it shares the backoffice's copy.
- Types come from the `@umbraco-cms/backoffice` npm package as a dev dependency, pinned to the same version as `Umbraco.Cms`.
- UI is built from the Umbraco UI Library (`uui-*` elements); backoffice services arrive through `consumeContext(...)`.

A v13 AngularJS property editor has no automatic path across the split: it is rewritten as a web component.

## Keep the loop tight

Umbraco is slow to boot, so a test that needs a running site is a slow loop. Put the logic in plain C# classes that take Umbraco's interfaces (or your own) as constructor parameters, test those directly, and leave controllers, composers and notification handlers as thin adapters over them.

## Upgrading across the split

Going from 13 to 17 is a project, not a package bump: backoffice extensions are rewritten and every package needs a version for the target major. Start from [Going from Umbraco 13 to 17](https://umbraco.com/blog/going-from-umbraco-13-to-17/) and the upgrade guide for the target major, list every `App_Plugins` folder and every Umbraco-dependent NuGet package with its status on the target, and give the user that inventory before any change.
